# 고객 현황 링크 유입 경로 설문

작성일: 2026-10-23 · 상태: 검토 대기 · 관련 설계: `2026-10-17-customer-progress-page-design.md`

## 1. 목적과 범위

계약한 고객이 위브디자인을 처음 어떻게 알게 됐는지 모아, 어느 홍보 채널이 실제 계약과 매출로 이어지는지 본다.

1. **고객 설문:** 고객 현황 링크에서 휴대폰 번호 뒷자리를 맞힌 다음, 그 현장에 답이 없으면 한 번 묻는다.
2. **현장 상세:** 현장 탭의 '고객 진행 현황 링크' 아래에서 그 현장의 유입 경로를 보고, 직원이 넣거나 고친다.
3. **경로별 통계:** 고객·현장 메뉴의 새 탭에서 경로마다 현장 수, 매출 합계, 현장당 평균을 본다.
4. **보기 관리:** 같은 탭에서 설문 보기를 더하고, 숨기고, 이름과 순서를 고친다.
5. **개인정보처리방침:** 유입 경로 수집과 목적을 한 줄씩 더한다(초안, 대표님 검토).

지금 상담 신청의 `source`는 어느 신청서로 들어왔는지(홈페이지 상담, 카카오 비즈니스폼)다. 이 설문은 처음 어떻게 알게
됐는지를 묻는다. 전화·방문으로 와서 `source`가 '직접 등록'뿐인 고객의 빈칸도 채운다.

성공 기준:

- 번호 확인을 마친 고객만 답할 수 있다. 한 현장에는 답이 하나만 남고, 두 번 눌러도 처음 답이 바뀌지 않는다.
- 답했거나, 건너뛰었거나, 직원이 넣은 현장의 고객에게는 다시 묻지 않는다.
- 현장 정보 저장(현장 탭)이 유입 경로를 덮어쓰거나 지우지 않는다.
- 보기 이름을 바꾸면 예전 답도 새 이름으로 묶이고, 보기를 숨겨도 예전 답은 통계에 남는다.
- 매출 합계는 매출 관리 권한이 있는 계정에만 보인다.
- 설문 화면은 휴대폰 한 화면 안에 들어온다(보기 2열).

### 결정 사항 (대표님 답변, 2026-10-23)

| 질문 | 결정 |
|---|---|
| 설문 시점 | 번호 확인 다음. 확인된 고객의 답만 저장한다 |
| 답 개수 | 하나만 ('가장 큰 계기') |
| 이미 링크를 쓰던 고객 | 다음에 링크를 열 때 한 번 묻는다 |
| 결과 보기 | 현장 상세 + 경로별 통계 (대시보드 요약은 하지 않음) |
| 보기 목록 | 관리자 화면에서 고칠 수 있다. 처음 목록은 지금 홍보 중인 곳 |
| 직원 입력 | 가능. 직원이 넣은 현장은 고객에게 묻지 않는다 |
| 건너뛰기 | 다시 묻지 않는다. 통계에 '건너뜀'으로 나온다 |
| 개인정보처리방침 | 초안을 넣고 PR에서 대표님이 문구를 확인한다 |
| 보기 배치 | 2열 버튼, 짧은 이름 (긴 세로 목록은 너무 길다는 의견) |

### 하지 않는 것

- 여러 개 고르기, 두 번째 질문, 만족도 같은 다른 설문.
- 대시보드 첫 화면 요약.
- 상담 신청서(홈페이지·카카오)에 같은 질문 넣기.
- 경로별 광고비 입력과 ROI 계산(매출 합계까지만).

## 2. 고객 흐름

```
링크 열기 → (쿠키 없음) 번호 뒷자리 확인 → 새로고침
          → (쿠키 있음) 이 현장에 acquisition이 없나?
                ├ 없음 → 설문 화면 → 답하기 / 건너뛰기 → 새로고침 → 공사 현황(공사 일정)
                └ 있음 → 공사 현황(공사 일정)
```

- 판단은 서버 페이지(`app/progress/[code]/page.tsx`)가 쿠키 확인 다음에 한다. `acquisition`이 없으면
  `ProgressView` 대신 설문 화면(`AcquisitionSurvey`, 클라이언트 부품)을 그린다.
- 화면 문구:
  - 위: "공사를 맡겨 주셔서 감사합니다"
  - 제목: "위브디자인을 처음 어떻게 알게 되셨나요?"
  - 설명: "더 좋은 서비스를 위해 한 가지만 여쭤볼게요. 답하지 않으셔도 괜찮아요."
- 보기는 2열 버튼이다. 고른 보기는 파란색으로 바뀐다. 맨 끝은 항상 '기타'이고, 고르면 직접 적는 칸(최대 40자)이 열린다.
- 아래 버튼:
  - **[답하고 공사 현황 보기]:** 보기를 고르기 전에는 누를 수 없다. '기타'는 내용을 적어야 누를 수 있다.
  - **[건너뛰기]:** 글자 링크 모양이다.
- 보낸 뒤에는 새로고침해서 서버가 공사 현황을 그린다. 보내기에 실패하면 화면에 오류를 보여 주고, 고른 답은 그대로 둔다.
- 관리자의 '미리보기'(고객 화면 미리보기)는 지금처럼 공사 현황만 보여 준다. 설문은 나오지 않는다.

## 3. 데이터

### 3.1 현장의 유입 경로 (`officeSites/<id>.acquisition`)

```ts
type SiteAcquisition = {
  status: 'answered' | 'skipped';
  optionId?: string;  // 고른 보기의 id. '기타'는 'other'
  label?: string;     // 답할 때의 보기 이름 (보기가 지워져도 통계에 이 이름으로 남는다)
  other?: string;     // '기타'에 적은 내용, 1-40자
  by: 'customer' | 'staff';
  staffId?: string;   // 직원이 넣었을 때 그 계정 loginId
  at: string;         // ISO 시각
};
```

- `acquisition`이 없는 현장은 '미응답'이다. 직원이 '지우기'를 누르면 칸이 없어지고, 고객은 다음 방문 때 다시 질문을 받는다.
- **서버만 쓰는 칸:**
  - 현장 저장(`/api/manager/office`)은 받은 현장 기록에서 `acquisition`을 버린다.
  - Firestore 저장 마스크에서도 뺀다(`SERVER_OWNED_SITE_FIELDS`와 같은 방식).
  - 그래서 오래 열어 둔 현장 폼이 답을 덮어쓰거나 지우지 못한다.
- **보내기는 한다:** 링크 코드와 달리 비밀이 아니다. 현장 기록을 브라우저로 보낼 때 `acquisition`은 그대로 둔다. 통계를
  브라우저에서 이미 읽은 현장·매출 목록으로 계산하기 위해서다(추가 읽기 없음).
- 위 두 규칙은 `app/api/manager/_site-fields.ts`에 상수 두 개로 나눠 적는다.
  - `SERVER_OWNED_SITE_FIELDS`: 숨기고 보호한다. 지금 있는 상수다.
  - `SERVER_WRITTEN_SITE_FIELDS = ['acquisition']`: 보호만 한다.
  - 받는 쪽 버리기와 저장 마스크는 둘을 합친 목록을 쓴다.
- `acquisition`만 고치는 쓰기도 다른 현장 수정처럼 `officeChanges`를 올린다. 열린 관리자 화면이 새 답을 받아 오게 하기
  위해서다. 링크 칸만 고치는 쓰기는 지금처럼 올리지 않는다.

### 3.2 보기 목록 (`managerSettings/acquisitionOptions`)

```ts
type AcquisitionOption = { id: string; label: string; hidden?: boolean };
// 문서: { options: AcquisitionOption[]; updatedAt: string; updatedBy: string }
```

- **처음 목록:** 문서가 없을 때 쓴다. 지금 홍보 중인 곳에 홍보 밖 경로를 더했다.

  | id | 보기 이름 |
  |---|---|
  | naver-place | 네이버 플레이스 |
  | homepage | 홈페이지·검색 |
  | blog | 블로그 |
  | instagram | 인스타그램 |
  | youtube | 유튜브 |
  | daangn | 당근마켓 |
  | zipdoc | 집닥 |
  | kakaotalk | 카카오톡 |
  | friend | 지인 소개 |
  | returning | 예전 고객 |
  | walk-in | 지나가다 봤어요 |

- '기타'(`id: 'other'`)는 목록에 저장하지 않는다. 언제나 맨 끝에 붙고, 숨기거나 이름을 바꿀 수 없다.
- **규칙**(`app/lib/acquisition.ts`, 테스트 대상):
  - 보기 이름은 앞뒤 공백을 빼고 1-12자다. 2열 버튼 한 칸에 들어가는 길이다.
  - 공백과 대소문자를 무시하고 이름이 겹치면 안 된다. '기타'와도 겹치면 안 된다.
  - 보기는 최대 20개다.
  - id는 `[a-z0-9-]{1,40}`이고, 새 보기는 서버가 만든다.
- 보기를 지우는 기능은 두지 않고 **숨기기**만 둔다. 숨긴 보기는 고객 설문에서만 빠지고, 현장 상세의 직원 선택과 통계에는
  남는다.

## 4. 서버

### 4.1 고객 답 받기 — `POST /api/progress/acquisition`

본문: `{ code, answer: { optionId, other? } }` 또는 `{ code, skip: true }`.

1. 형식 검사를 한다. 코드 모양이 틀리거나 저장소가 준비되지 않았으면 링크가 꺼졌을 때와 같은 404를 준다(verify와 같은 규칙).
2. 코드로 현장을 찾는다. 휴지통, 꺼진 링크, 바뀐 코드는 모두 404다.
3. **쿠키를 확인한다.** `verifyProgressCookie(쿠키, code, progressPhoneDigits(resolveCustomerPhone(site)), key)`.
   통과하지 못하면 401 "본인 확인이 필요합니다. 페이지를 새로고침해 주세요."를 준다. 화면은 새로고침해서 번호 확인으로 돌아간다.
4. 현장을 버전과 함께 다시 읽는다(`getSiteForProgressWithVersion`). 이미 `acquisition`이 있으면 바꾸지 않고 200
   `{ ok: true }`를 준다. 두 번 눌러도 처음 답이 남는다.
5. **답을 검사한다.** `optionId`는 숨기지 않은 보기이거나 'other'여야 한다. 'other'는 `other`가 1-40자여야 한다(줄바꿈과 제어
   문자는 빼고 공백은 하나로 줄인다). 그 밖에는 400이다.
6. `acquisition`만 쓰는 마스크 쓰기를 읽은 버전 조건(`updateTime`)으로 한다.
   - 충돌하면 한 번 다시 읽는다. 그사이 답이 생겼으면 200을 준다. 아니면 503 "잠시 후 다시 시도해 주세요."를 준다.
7. 응답은 `Cache-Control: private, no-store`다. 답 내용과 코드는 로그에 남기지 않는다.

### 4.2 관리자 — `/api/manager/acquisition`

모든 요청에 `sites` 권한이 필요하다(관리자는 모든 권한을 가진다).

- `GET`: 보기 목록(처음 목록 포함)을 준다.
- `POST { action: 'saveOptions', options }`:
  - 3.2 규칙으로 검사하고, 새 보기에 id를 붙여 저장한다.
  - 저장은 읽은 버전 조건으로 한다. 다른 사람이 먼저 고쳤으면 409를 주고 화면은 다시 불러온다.
- `POST { action: 'setSite', siteId, optionId, other? }`:
  - 직원이 넣거나 고친다. `by: 'staff'`, `staffId`, `at`을 남긴다.
  - 숨긴 보기도 고를 수 있다. 예전 답을 그대로 고칠 때를 위해서다.
- `POST { action: 'clearSite', siteId }`: 칸을 지운다. 고객은 다음 방문 때 다시 질문을 받는다.
- 현장 쓰기는 3.1의 마스크 쓰기(`acquisition`만)로 하고, 휴지통 현장은 404다.

### 4.3 고객 페이지 읽기

- 쿠키 확인 다음에 `acquisition`이 없을 때만 보기 목록을 읽는다(Firestore 읽기 1번).
- 보기 목록을 읽지 못하면 설문 없이 공사 현황을 보여 준다. 설문 때문에 고객이 현황을 못 보는 일은 없게 한다.

## 5. 관리자 화면

### 5.1 현장 상세 — '유입 경로' 칸

- 현장 탭에서 현장을 고르면 나오는 `ProgressLinkPanel` 바로 아래에 둔다. 링크가 없는 현장에서도 보인다.
- **보이는 내용:**
  - 답이 있으면 보기 이름(기타는 적은 내용)과 표시, 날짜가 보인다.
    - 고객이 답했으면 '고객 답변', 직원이 넣었으면 '직원 입력 · 이름'으로 표시한다.
  - 건너뛰었으면 '건너뜀'이 보인다.
  - 답이 없으면 '아직 답이 없어요'가 보인다.
- **[고치기 / 직원이 입력]:** 보기 선택(숨긴 보기 포함)과 기타 내용, [저장] [취소]가 나온다.
- **[지우기]:** 확인 창을 거친다. "지우면 고객이 다음에 링크를 열 때 다시 묻습니다."
- 저장하면 화면의 현장 목록에 돌아온 `acquisition`을 넣는다.

### 5.2 새 탭 '유입 경로'

고객·현장 메뉴(`customer-work`)에 탭 하나를 더한다. `sites` 권한이 있는 계정에 보인다.

- **왼쪽: 경로별 통계**
  - 기간 고르기: 이번 달 / 최근 3개월 / 올해 / 전체.
  - 표: 유입 경로, 현장 수(막대), 매출 합계, 현장당 평균. 맨 아래 '건너뜀', '미응답'은 흐리게 보인다.
  - 매출 두 칸은 `sales` 권한이 있는 계정에만 보인다. 없으면 그 열이 아예 없다.
  - 경로를 누르면 그 경로의 현장 목록(현장명, 고객명, 기타 내용, 고객/직원, 날짜)이 펼쳐진다.
- **오른쪽: 설문 보기 관리**
  - 보기 이름(고치기), ↑ ↓, 숨기기/보이기, [＋ 보기 추가], [저장].
  - '기타(직접 입력)'은 맨 아래에 고정이다.
  - 안내: "숨겨도 예전 답은 통계에 남아요. 이름을 바꾸면 예전 답도 새 이름으로 묶여요."

## 6. 통계 규칙 (`acquisitionStats`, `app/lib/acquisition.ts`)

입력: 현장 목록, 매출 목록, 보기 목록, 기간(서울 날짜 `from`~`to`, '전체'는 제한 없음).

- **세는 현장:**
  - 휴지통이 아닌 현장 가운데, 등록일(`createdAt`, 서울 날짜)이 기간 안이어야 한다.
  - 상태가 계약·시공중·완료이거나, `acquisition`이 있어야 한다.
  - 상담 중인 현장이 '미응답'을 부풀리지 않게 하기 위해서다.
- **묶기:**
  - `answered`는 `optionId`로 묶고, 이름은 지금 보기 이름을 쓴다. 보기가 목록에 없으면 저장된 `label`을 쓴다.
  - 'other'는 '기타' 하나로 묶고, 펼친 목록에 적은 내용이 보인다.
  - `skipped`는 '건너뜀', 칸이 없으면 '미응답'이다.
- **매출 합계:**
  - 그 현장들의 매출 기록(`siteId`)의 `amount` 합이다. 입금일 기간과는 관계없다.
  - 상태가 '견적'·'취소'인 매출은 뺀다(`NON_REVENUE_SALE_STATUSES`, 대시보드와 같은 규칙).
- **순서:** 현장 수가 많은 순이다. 같으면 보기 목록 순서를 따르고, '기타' → '건너뜀' → '미응답'은 맨 끝이다.
- **현장당 평균:** 매출 합계 ÷ 현장 수(반올림)다.

## 7. 개인정보처리방침 (`app/privacy/page.tsx`, 초안)

- **수집하는 개인정보**에 덧붙인다: "공사 진행 현황 링크에서 고객이 선택해 답한 유입 경로(예: 네이버 플레이스, 지인 소개)를
  수집할 수 있습니다."
- **이용 목적**에 덧붙인다: "유입 경로는 홍보 채널 분석과 서비스 개선에만 사용합니다."
- 문구는 PR에서 대표님이 확인한다. 설문을 배포하는 PR에 함께 넣어서, 방침보다 수집이 먼저 시작되지 않게 한다.

## 8. Firestore 사용량

- **고객 설문:** 현장당 한 번이다.
  - 페이지에서 보기 목록 읽기 1번이 든다.
  - 답하기에는 코드 찾기 1번, 현장 다시 읽기 1번, 보기 목록 1번, 쓰기 1번이 든다. 고객 번호를 고객 기록에서 찾아야
    하는 현장은 읽기가 1번 더 든다(verify와 같다).
  - 답이 있는 현장은 추가 읽기가 없다.
- **직원 입력:** 현장 읽기 1번과 쓰기 1번이 든다.
- **통계:** 관리자 화면이 이미 읽은 현장·매출 목록으로 계산한다. 탭을 열 때 보기 목록만 1번 읽는다.
