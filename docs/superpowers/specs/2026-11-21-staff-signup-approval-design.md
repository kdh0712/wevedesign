# 직원 가입 링크와 총괄 승인

작성일: 2026-11-21 · 상태: 설계 승인(2026-11-21) · 관련 설계: `2026-10-17-manager-auth-hardening-design.md`, `2026-10-20-staff-mobile-app-design.md`

## 1. 목적과 범위

지금은 총괄 관리자가 직원의 아이디와 비밀번호를 직접 정해 계정을 만들고 알려 줘야 한다. 앞으로는:

1. 총괄이 **가입 링크**를 만들어 새 직원에게 보낸다(카톡 등).
2. 직원이 링크에서 **이름·휴대폰·아이디·비밀번호**를 직접 적어 **가입 요청**을 보낸다.
3. 총괄이 계정 권한 탭에서 요청을 보고 **역할과 권한을 골라 승인**하거나 거절한다.
4. 승인된 직원은 PC 관리 화면과 휴대폰 앱에서 그 아이디·비밀번호로 로그인한다.

성공 기준:

- 승인 전에는 그 아이디로 로그인할 수 없다(권한 0개로 들어가는 것도 안 됨).
- 비밀번호 원문은 서버 어디에도(저장소·로그·응답) 남지 않는다. 총괄도 직원 비밀번호를 모른다.
- 링크 하나로 가입 요청은 하나만 생기고, 만료·취소·사용된 링크는 다시 쓸 수 없다.
- 승인한 계정은 기존 계정과 같은 화면에서 보이고, 권한 수정·비활성화가 된다.
- 링크 주소가 검색·다른 사이트·분석 도구로 새지 않는다.

### 결정 사항 (사용자 답변, 2026-11-21)

| 질문 | 결정 |
|---|---|
| 가입한 직원 계정을 어디에 만드나 | **새 아이디 계정(Firestore `managerAccounts`)**. 이메일이 아닌 아이디로 로그인 |
| 링크 방식 | **1인 1링크**. 요청 하나로 끝, 기본 7일 뒤 만료, 총괄이 취소 가능 |
| 권한은 언제 정하나 | 승인할 때 총괄이 고른다(링크를 만들 때는 정하지 않음) |
| 직원 개인정보 안내·보관 | **A안**: 가입 화면에 짧은 안내, 승인되지 않은 요청은 30일 뒤 삭제, 계정을 끌 때 휴대폰 번호도 삭제. 공개 개인정보처리방침은 고객용이라 그대로, 동의 체크 칸은 두지 않음 |

### 하지 않는 것

- 가입 요청 알림(알림톡·푸시). 총괄은 계정 권한 탭과 사이드바 배지로 안다.
- 기존 Firebase 이메일 계정·Sanity 아이디 계정을 새 저장소로 옮기기.
- 비밀번호 찾기·직원 스스로 비밀번호 바꾸기.
- 여러 명이 같이 쓰는 가입 링크.
- 이미 로그인한 PC 세션을 즉시 끊기(지금처럼 최대 8시간, 휴대폰은 1시간 안에 끝남).

### 실패로 보는 것

- 링크만 있으면 승인 없이 무엇이든 볼 수 있게 되는 것.
- 비밀번호를 평문으로 잠깐이라도 저장하는 것(승인 때까지 보관하는 방식 포함).
- 직원(staff)이 가입 링크를 만들거나 요청을 승인하는 것.

## 2. 방법 비교 (고른 것: A)

| | A. Firestore 아이디 계정 (선택) | B. Firebase 이메일 계정 | C. Sanity 아이디 계정 |
|---|---|---|---|
| 로그인 아이디 | 아이디(요청 그대로) | 이메일 | 아이디 |
| 비밀번호 | 요청 순간 scrypt 해시, 원문 버림 | Firebase 계정을 만들려면 원문이 필요 → 요청 때 '비활성' 사용자를 미리 만들고 거절 시 삭제 | 해시 |
| 위험 | 새 저장소 하나 추가 | 프로필 없는 이메일 사용자를 권한 0개로 들여보내는 기존 경로(`_login.ts`)에 걸리기 쉬움 | Sanity 무료 요금제는 데이터셋을 비공개로 못 해 해시가 노출될 수 있음 |

A를 고른 이유: 요청하신 '아이디' 로그인과 맞고, 비밀번호 원문을 보관할 필요가 없으며, 서버만 쓰는 Firestore 컬렉션은 이미 `managerDevices`·`siteNotes`에서 쓰는 방식이다.

## 3. 화면 흐름

### 3.1 총괄: 가입 링크 만들기 (계정 권한 탭)

```
가입 링크                                            [가입 링크 만들기]
  현장팀 박OO   · 만든 사람 admin · 11/28까지   [취소]
  디자인 이OO   · 만든 사람 김동호 · 11/25까지  [취소]
```

- [가입 링크 만들기] → 작은 창: **누구에게**(메모, 1~30자, 필수), **유효기간**(1일 / 3일 / 7일, 기본 7일) → [만들기].
- 만들면 링크를 **한 번만** 보여 준다(저장소에는 해시만 있어 다시 못 보여 줌): `https://www.wevedesign.co.kr/manager-weve-7519/join#<토큰>` + [복사]. "이 창을 닫으면 링크를 다시 볼 수 없습니다. 잃어버리면 취소하고 새로 만드세요."
- 목록에는 아직 쓰이지 않은 유효한 링크만 보인다. 만료·사용·취소된 링크는 목록에서 빠진다.

### 3.2 직원: 가입 요청

`/manager-weve-7519/join#<토큰>` (휴대폰에서 주로 연다)

```
위브디자인 직원 가입
  이름            [          ]
  휴대폰          [010-    -    ]
  아이디          [          ]  영문 소문자·숫자 4~20자
  비밀번호        [          ]  8자 이상
  비밀번호 확인   [          ]
  이름·휴대폰은 직원 계정 확인과 업무 연락에만 씁니다.
  승인되지 않은 요청은 30일 뒤 지워집니다.
                       [가입 요청]
```

- 페이지가 열리면 토큰을 서버에 확인한다. 쓸 수 없는 링크(없음·만료·취소·사용됨)는 모두 같은 문구: "쓸 수 없는 링크입니다. 총괄 관리자에게 새 링크를 받아 주세요." (어느 이유인지 알려 주지 않음)
- 요청을 보내면: "가입 요청을 보냈습니다. 총괄 관리자가 승인하면 이 아이디로 로그인할 수 있습니다." + [로그인 화면으로]. 같은 링크를 다시 열면 '쓸 수 없는 링크'.
- 아이디가 이미 쓰이고 있으면 요청 전에 그 자리에서 알린다("이미 사용 중인 아이디입니다"). 링크는 소진되지 않는다.
- 화면 색은 관리 화면 로그인 화면과 같은 체계(청회색·청록)를 쓴다.

### 3.3 총괄: 승인·거절

계정 권한 탭 맨 위(요청이 있을 때만), 사이드바 '계정 권한'에 대기 건수 배지(총괄에게만).

```
가입 요청 1건
┌───────────────────────────────────────────────┐
│ 박OO · 010-1234-5678 · 아이디 park01            │
│ 11/21 14:02 요청 · 링크: 현장팀 박OO             │
│ 역할  (•) 직원  ( ) 총괄 관리자                   │
│ 빠른 선택 [현장팀] [견적·디자인] [사무]             │
│ ☑ 업무 현황 ☐ 상담 ☐ 고객 ☑ 현장 ☐ 견적 …         │
│                              [거절]  [승인]     │
└───────────────────────────────────────────────┘
```

- 권한 체크는 지금 계정 폼과 같은 목록(`MANAGER_PERMISSIONS`, `accounts` 제외)과 같은 규칙(총괄은 전부)을 쓴다.
- 빠른 선택은 체크를 채워 줄 뿐이고, 고친 뒤 승인할 수 있다. 처음 묶음(내 판단, 고치기 쉬움):
  - 현장팀: `dashboard`, `sites`
  - 견적·디자인: `dashboard`, `customers`, `sites`, `estimates`
  - 사무: `dashboard`, `consultations`, `customers`, `sites`, `sales`
- 승인에는 권한을 하나 이상 고르거나 총괄을 골라야 한다.
- [거절]은 확인을 한 번 묻고 요청을 지운다.
- 승인하면 계정 목록에 바로 나타나고 요청 카드는 사라진다.

### 3.4 승인 뒤

- 직원은 PC(`/manager-weve-7519`)와 휴대폰 앱에서 아이디·비밀번호로 로그인한다. 로그인 칸의 이름은 "아이디 또는 이메일"로 바꾼다.
- 총괄은 계정 목록에서 이 계정의 이름·휴대폰·역할·권한·사용 여부를 고치고, 비밀번호를 새로 정해 줄 수 있다(직원이 잊었을 때).

## 4. 데이터

모두 Firestore, 서버 서비스 계정만 읽고 쓴다. Firestore 보안 규칙(콘솔)에서 세 컬렉션 모두 클라이언트 읽기·쓰기를 막는다(`managerDevices`와 같이). Firestore 규칙은 허용만 있어서(맞는 allow가 하나라도 있으면 허용) 막는 규칙을 더하는 것으로는 부족하고, 이 세 경로에 맞는 allow가 하나도 없어야 한다(`match /{document=**}` 같은 와일드카드 포함). 두 번째 방어(최종 검토 뒤 추가): 아이디 계정은 저장된 값이 scrypt 해시일 때만 로그인에 쓰고, 승인은 예약어 아이디나 scrypt 해시가 아닌 요청을 거부한다.

### 4.1 `managerSignupLinks`

- 문서 id: 토큰의 SHA-256(hex). 토큰은 32바이트 무작위(base64url), 서버가 만든다. 원래 토큰은 저장하지 않는다.
- 필드: `memo`, `createdBy`(loginId), `createdByName`, `createdAt`, `expiresAt`, `status`(`open` | `used` | `revoked`), `usedAt?`, `requestId?`.

### 4.2 `managerSignupRequests`

- 문서 id: 무작위.
- 필드: `name`, `phone`(숫자만, 휴대폰), `loginId`(정규화한 값), `passwordHash`(`_password.ts`의 scrypt 형식), `linkId`, `linkMemo`, `createdAt`.
- 승인·거절하면 문서를 지운다(거절한 사람의 해시를 남기지 않음).
- **30일 보관**: `createdAt`에서 30일이 지난 요청은 승인할 수 없고 목록에 보이지 않는다. 지우기는 따로 예약 작업을 두지 않고, 총괄 API가 요청 목록을 읽을 때 지난 요청을 함께 지운다(실패해도 목록 응답은 그대로, 로그만). 공개 API의 아이디 중복 확인도 지난 요청은 세지 않는다.

### 4.3 `managerAccounts`

- 문서 id: `acct-` + 정규화한 loginId의 SHA-256 앞 24자. 같은 아이디는 같은 문서 id라서 두 요청을 동시에 승인해도 `exists:false` 조건으로 하나만 만들어진다.
- 필드: `name`, `phone`, `loginId`, `passwordHash`, `role`(`admin` | `staff`), `permissions`, `isActive`, `createdAt`, `updatedAt`, `approvedBy?`, `approvedAt?`, `origin`(`signup` | `admin`).
- 지우지 않고 `isActive:false`로 끈다(Firebase 계정과 같은 동작). **끌 때 `phone`도 지운다**(A안). 다시 켤 때 휴대폰은 빈칸이고, 총괄이 다시 넣을 수 있다. 이름·아이디·해시는 다시 켤 수 있도록 남긴다.
- (2026-11-22 추가) 끈 계정은 총괄이 **삭제**할 수 있다. 끄기 → 삭제 두 단계라서 쓰고 있는 계정을 한 번에 지우지 않는다. 삭제하면 문서가 없어지고 그 아이디는 다시 가입에 쓸 수 있다. 서버는 읽은 순간 꺼져 있던 판(`updateTime` 조건)만 지운다. 같은 아이디로 새 계정이 생겨도 예전 휴대폰은 비밀번호 해시가 달라 로그인되지 않는다.

### 4.4 규칙 (순수 모듈 `app/lib/staff-signup-rules.ts`, import 없음)

- **아이디 정규화**: 앞뒤 공백 제거 후 소문자. 형식 `^[a-z0-9._-]{4,20}$`. `@`는 형식에서 빠지므로 이메일 로그인과 겹치지 않는다. 예약어 `admin`, `manager` 불가.
- **비밀번호**: 지금 로그인이 비밀번호 앞뒤 공백을 자르므로(`_login.ts`), 해시도 자른 값으로 만든다. 자른 뒤 8~72자.
- **이름** 1~30자, **휴대폰**은 `normalizeKoreanMobile`이 받는 번호만.
- **링크 상태**: `open`이고 `expiresAt`이 지나지 않았을 때만 쓸 수 있다. 유효기간은 1·3·7일 중 하나.
- **빠른 선택 묶음**과 승인 입력 검사.

## 5. 서버

### 5.1 총괄 전용 API — `app/api/manager/signup/route.ts`

`requireManager({ admin: true })`(마스터 비밀번호 세션 포함). 작업 규칙대로 모든 manager API는 세션을 확인한다.

- `GET` → 열린 링크 목록(만료 안 된 `open`), 대기 요청 목록(해시 제외, 30일 안 된 것만. 지난 요청은 이때 지움, 4.2).
- `POST { action: 'createLink', memo, days }` → 토큰을 만들어 해시로 저장하고, 응답에 **링크 주소를 한 번** 담는다.
- `POST { action: 'revokeLink', id }` → `open`인 링크만 `revoked`로(버전 조건).
- `POST { action: 'approve', requestId, role, permissions }` → 아이디가 기존 계정(`managerAccounts`, 같은 loginId의 Sanity `managerAccount`)과 겹치지 않는지 다시 확인 → `managerAccounts`를 `exists:false`로 만들기(겹치면 409 "이미 같은 아이디 계정이 있습니다") → 요청 삭제. `approvedBy`에 승인한 세션의 loginId.
- `POST { action: 'reject', requestId }` → 요청 삭제.
- 승인·거절은 요청을 읽은 버전 조건으로 지운다(둘이 동시에 처리하면 한쪽만 성공, 다른 쪽은 "이미 처리된 요청입니다").
- Sanity 아이디 중복 확인은 대소문자를 무시하고 비교한다.
- 꺼진(`isActive:false`) 아이디 계정의 아이디는 다시 쓸 수 없다(문서 id가 아이디에서 나옴). 같은 사람이 돌아오면 총괄이 그 계정을 다시 켜고 비밀번호를 새로 정한다.
- 링크 주소는 요청이 들어온 사이트 주소(origin)로 만든다(미리보기 배포에서 만든 링크는 그 미리보기로).
- Firestore 서비스 계정이 없으면 503 "가입 링크 기능은 Firestore 서비스 계정 설정이 필요합니다."

### 5.2 공개 API — `app/api/staff-signup/route.ts`

세션 없이 부른다. `/api/manager/` 아래에 두지 않는다(그 아래는 모두 세션 필수). 토큰은 주소창의 `#` 뒤에만 있으므로 서버 로그·Referer·분석 도구로 가지 않는다. 브라우저는 POST 본문으로만 보낸다.

- `POST { action: 'check', token }` → `{ ok: true }` 또는 `{ ok: false }`(이유 구분 없음).
- `POST { action: 'checkLoginId', token, loginId }` → 쓸 수 있는 아이디인지(형식·예약어·기존 계정·대기 요청). 유효한 토큰이 있을 때만 답한다.
- `POST { action: 'submit', token, name, phone, loginId, password, website, startedAt }`
  1. 남용 방지(5.3)와 입력 검사.
  2. 링크를 버전과 함께 읽고 쓸 수 있는지 확인.
  3. 아이디 중복 확인(기존 계정·대기 요청).
  4. 비밀번호를 scrypt로 해시(원문은 이 함수 밖으로 나가지 않음).
  5. 링크를 `used`로 바꾸는 쓰기를 읽은 버전 조건으로 한다 → 지면 '쓸 수 없는 링크'.
  6. 요청 문서를 만든다. 실패하면 링크를 다시 `open`으로 돌려 직원이 같은 링크로 다시 시도할 수 있게 한다(그 되돌리기가 실패하면 로그만 남김).
- 같은 아이디로 동시에 두 요청이 들어와 둘 다 대기로 남는 경우는 승인 단계의 `exists:false`가 막는다(두 번째 승인은 409).

### 5.3 남용 방지

- 서버 메모리 제한기(`_login-limit.ts`의 `createLoginLimiter`와 같은 방식): 접속 주소마다 15분에 `check`·`checkLoginId` 30회, `submit` 5회. 틀린 토큰도 센다.
- 상담 폼과 같은 숨은 칸(`website`)과 최소 입력 시간(`startedAt`, 3초). 걸리면 성공처럼 답하고 아무것도 저장하지 않는다(`consultation-guard.ts`와 같은 태도).
- 접속 주소, 토큰, 비밀번호, 휴대폰 번호는 로그에 남기지 않는다.

### 5.4 로그인과 세션

- 세션 출처(`SessionSource`, `AccountSource`, 휴대폰 기기의 `src`)에 `firestore`를 더한다.
- `verifyManagerLogin`(`_login.ts`): `@`가 없는 아이디는 마스터 확인 → **`managerAccounts`(정규화한 아이디의 문서 id)와 Sanity `managerAccount`(지금처럼 원래 값 그대로)를 동시에 읽고**, Firestore 계정이 있으면 그것을, 없으면 Sanity 계정을 쓴다. 차례로 읽으면 두 번째 조회 시간 때문에 계정 존재가 드러나므로 동시에 읽는다. 비밀번호 확인(`verifyPasswordOrDummy`)은 한 번만 한다. `isActive:false` 계정은 없는 것처럼 '계정 또는 비밀번호가 올바르지 않습니다'(Sanity 계정과 같은 동작). 서비스 계정이 없으면 Firestore 조회를 건너뛴다. 결과는 `src:'firestore'`, `credential: passwordHash`.
- `reloadManagerUser('firestore', id)`: 문서를 다시 읽어 없거나 꺼졌으면 `null`(휴대폰 로그아웃), 아니면 역할·권한을 새로 읽고 `credential`로 해시를 돌려준다. 비밀번호를 바꾸면 휴대폰 기기의 도장(`credentialStamp`)이 맞지 않아 로그아웃된다.
- `reloadSourceOutage`: `firestore` 출처인데 서비스 계정이 없으면 장애로 본다(계정 삭제로 보지 않음, 휴대폰은 기기를 유지).
- 세션 토큰과 `requireManager`는 그대로(서명된 역할·권한, PC 8시간).

### 5.5 계정 API — `app/api/manager/accounts/route.ts`

- `GET`: 지금 목록(Firebase 모드면 Firebase 계정, 아니면 Sanity 계정)에 **`managerAccounts`를 더해** 돌려준다. 각 항목에 `kind`(`firebase` | `sanity` | `id`)와 `phone`(아이디 계정)을 붙인다.
- `POST`: `kind:'id'`이면 `managerAccounts`를 고친다(이름·휴대폰·역할·권한·사용 여부, 비밀번호를 넣으면 새 해시). 권한 정규화 규칙은 그대로(`normalizePermissions`, 총괄은 전부).
- 총괄이 직접 계정을 만들 때(내 판단): 아이디에 `@`가 있고 Firebase 모드면 지금처럼 Firebase 이메일 계정, `@`가 없으면 **아이디 계정**(`origin:'admin'`)으로 만든다. 아이디·비밀번호 규칙은 4.4와 같다.
- `DELETE`: `kind:'id'`는 `isActive:false`와 함께 `phone`을 지운다. `POST`로 사용 여부를 끌 때도 같다(4.3). `permanent: true`를 더하면 이미 끈 계정만 문서를 지운다(켜져 있으면 409).

## 6. 관리 화면

- 계정 권한 탭에 `signup-panel.tsx`(별도 부품, `mobile-devices-panel.tsx`처럼)를 더한다: 가입 요청 카드 → 가입 링크 목록 순서로, 계정 목록 위.
- 계정 목록은 종류를 작은 꼬리표로 보여 준다(아이디 / 이메일). 아이디 계정은 휴대폰 번호도 보여 준다.
- 사이드바 '계정 권한'의 배지: 총괄이 로그인했을 때 요청 수를 한 번 읽고, 계정 권한 탭에서 승인·거절하면 갱신한다. 실시간이 아니어도 된다.
- 가입 페이지 `app/manager-weve-7519/join/page.tsx`: 로그인 없이 열리는 클라이언트 페이지. `/manager-weve-7519/` 아래라 `noindex`·`no-store`를 그대로 받는다. 이 경로에 `Referrer-Policy: no-referrer`를 더한다(`next.config.ts`). 관리 화면의 로그인 확인·대시보드 코드를 불러오지 않는다.
- 분석: 관리 화면에는 네이버 분석이 없다(작업 규칙). Vercel Analytics가 이 경로를 기록하더라도 토큰은 `#` 뒤라 주소에 실리지 않는다. 빌더는 실제로 그런지 확인하고, `#` 뒤까지 보낸다면 `/progress`처럼 주소를 지워서 보낸다(`app/lib/site-analytics.tsx`).
- 빠른 선택 묶음의 `customers` 권한: 고객·현장 탭 합치기(`2026-11-21-customer-site-merge-design.md`) 뒤에도 '고객 정보' 권한은 남으므로 묶음은 그대로 쓸 수 있다.

## 8. 작업 규칙 문서 (`docs/WEVE_WORKING_RULES.md`)

"Manager Authentication"에 'Staff sign-up' 단락을 더한다: 1인 1링크·해시만 저장·`#` 토큰, 승인 전 로그인 불가, 비밀번호는 요청 순간 해시, `managerSignupLinks`·`managerSignupRequests`·`managerAccounts`는 서버만(보안 규칙으로 클라이언트 차단), 공개 API의 남용 방지, 아이디 규칙과 예약어, `firestore` 세션 출처의 다시 읽기·장애 규칙, 직원 정보 보관(가입 화면 안내 문구, 대기 요청 30일 뒤 삭제, 계정을 끌 때 휴대폰 삭제. 안내 문구와 이 규칙은 같이 고친다).

## 9. 배포 순서

1. Firestore 콘솔에서 세 경로(`managerSignupLinks`·`managerSignupRequests`·`managerAccounts`)에 맞는 allow 규칙이 하나도 없는지 확인하고, 있으면 그 부분만 고친다(다른 앱과 같이 쓰는 데이터베이스). 새 컬렉션이라 코드보다 먼저 해도 아무것도 깨지지 않는다(최종 검토 뒤 순서를 바꿈).
2. 코드 배포(서비스 계정이 이미 있는 운영 환경 기준).
3. `managerAccounts`에 예상한 문서만 있는지 확인한다.
4. 운영에서 총괄이 링크를 하나 만들어 테스트 가입 → 승인 → PC·휴대폰 로그인 → 비활성화 후 휴대폰이 1시간 안에 로그아웃되는지 확인.
