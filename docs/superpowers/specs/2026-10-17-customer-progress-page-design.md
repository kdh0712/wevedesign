# 고객 공사 진행 현황 페이지 설계

작성일: 2026-10-17 · 상태: 구현 완료, 최종 검토 수정 반영 (미리보기 확인 대기) · 병합: 앞선 묶음(#7·#8·#9·휴지통·보안)은 main에 병합됨, 이 기능은 다음 묶음

## 1. 목적

계약한 고객이 알림톡 버튼 하나로 자기 현장의 공사 진행 상황(사진, 공정, 작업 메모)을 확인하게 한다. 지금은 직원이
일일 보고서 이미지를 만들어 내려받고 카톡으로 따로 보내며, 기록은 그 PC 브라우저에만 남는다.

### 결정 사항 (대표님 답변)

| 질문 | 결정 |
|---|---|
| 보낼 안내 | 사진과 진행 현황 링크 (고객용 페이지 + 알림톡 버튼) |
| 페이지 내용 | 날짜별 현장 사진, 공정 일정과 진행률, 작업 메모, 연락처 |
| 고객 확인 | 비밀 링크 + 휴대폰 번호 뒷자리 4자리 |
| 알림톡 발송 | 직원이 올릴 때 골라서 발송 (자동 발송 없음) |
| 올리는 곳 | 기존 일일 보고서 창 |
| 구현 방식 | A안: Firestore 기록 + Sanity 사진 + 홈페이지 안 고객 페이지 |
| 연락처 | 회사 대표번호(031-381-0489)만 |
| 병합 시점 | 다음 묶음. 보안 강화 작업 위에서 만든다 |
| 링크 생성 (2026-10-17) | 처음 올릴 때 자동 |
| 링크 종료 (2026-10-17) | '완료'로 바뀌는 즉시 자동. 이미 완료된 현장은 자동으로 열지 않는다 |

## 2. 저장 구조

### 진행 기록: Firestore `siteProgressUpdates`

| 필드 | 내용 |
|---|---|
| `siteId` | 현장 ID |
| `reportDate` | 작업 날짜 (`YYYY-MM-DD`) |
| `designer` | 담당 실장 이름 (일일 보고서 입력값) |
| `workDetail` | 작업 메모 (줄바꿈 유지) |
| `photos` | `[{ assetId, url, width, height }]` (올린 순서 유지) |
| `createdAt`, `createdBy` | 올린 시각, 올린 계정 |
| `notifyLog` | `[{ sentAt, ok, error?, by }]` 알림톡 발송 기록 |

### 현장 정보 추가 필드 (`officeSites`)

| 필드 | 내용 |
|---|---|
| `progressCode` | 진행 현황 코드. `crypto.randomBytes(16)`의 base64url (22자) |
| `progressEnabled` | 링크 켜기/끄기 |
| `progressCodeCreatedAt` | 코드를 만든 시각 |
| `progressAccess` | `{ failedCount, lockedUntil, lockCount?, lastOkAt? }` 뒷자리 확인 실패 기록과 잠금. `lockCount`는 마지막 성공 뒤 잠긴 횟수, `lastOkAt`은 마지막으로 맞게 입력한 시각 |

이 네 필드(`progressCode`, `progressEnabled`, `progressCodeCreatedAt`, `progressAccess`)는 서버만 쓴다. 쓰는 곳은 셋이다.

- 진행 현황 API(`/api/manager/progress`): 링크 켜기·끄기·새 링크(`setLink`)와 첫 기록의 링크 생성.
- 확인 API(`/api/progress/verify`): `progressAccess`.
- 현장 저장(`/api/manager/office`) 뒤에 도는 '완료' 자동 종료: `progressEnabled`.

`progressAccess`는 두 곳이 쓴다. 확인 API가 쓰고, `/api/manager/progress`가 새 코드를 만들 때(새 링크로 바꾸기, 처음 만들기) 처음 상태로 비운다. 세 곳 모두 이 필드만, 마스크를 건 Firestore 쓰기(`updateMask`)로 쓰므로 같은 현장의 다른 수정을 되돌리지 못한다. 현장 저장 자체는 자기 쓰기에서 이 필드들을 뺀다 (휴지통 이동·복구도 같다).

### 사진

- 브라우저에서 긴 변 1600px, JPEG 품질 0.82로 줄인 뒤 올린다. 모든 사진을 다시 저장하므로 카메라 정보(위치 포함)는 사라진다.
- 저장은 프로젝트 사진과 같은 Sanity 에셋 업로드 흐름을 쓴다 (`SANITY_WRITE_TOKEN`, 서버 경유). Firebase Storage는
  쓰지 않는다 (`docs/WEVE_WORKING_RULES.md`).
- 고객 페이지는 Sanity 이미지 CDN의 크기 변환을 쓴다 (목록 `w=800`, 크게 보기 `w=1600`), 지연 로딩.
- 사진은 `progress-<무작위 16진수 12자>.<jpg|png|webp>`라는 중립적인 이름으로 올린다. 휴대폰의 원래 파일 이름에 고객 이름이
  들어갈 수 있고, Sanity가 그것을 `originalFilename`으로 남기기 때문이다.
- 공개 데이터셋은 누구나 토큰 없이 이미지 에셋 목록을 볼 수 있다. 그래서 올리기 전에 서버가 토큰 없이 Sanity에 물어보고
  (`app/api/manager/_sanity-privacy.ts`), 비공개가 확실할 때만 올린다. 공개이거나 확인하지 못하면 막는다 (§6). 비공개라는
  답은 10분 동안 기억한다. 배포 전 준비는 §8.
- Sanity 에셋 주소는 데이터셋이 비공개여도 주소를 알면 열린다. 주소에 추측할 수 없는 해시가 들어가므로 비밀 링크와 같은
  수준으로 본다.

### 기존 기능

- 일일 보고서의 로고 이미지 만들기·내려받기와 브라우저 저장 기록은 그대로 둔다. 옛 기록을 옮기지 않는다.
- 진행 기록을 지우면 고객 페이지에서 바로 사라진다. Sanity 에셋은 지우지 않는다 (다른 곳에서 참조 가능성, 복구 여지).

## 3. 고객 페이지

### 주소와 응답

- `app/progress/[code]/page.tsx` 서버 컴포넌트. `dynamic = 'force-dynamic'`, 메타데이터 `robots: noindex, nofollow`.
- 응답 헤더 `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer` (`next.config.ts`).
  주소의 코드가 리퍼러로 다른 곳에 넘어가지 않게 한다. 사이트맵·RSS에 넣지 않는다.
- 분석 도구: 주소의 코드는 링크의 열쇠라서 분석 도구와 로그에 남기지 않는다. `/progress`에서는 네이버 wcslog를 불러오지 않고,
  Vercel Analytics는 주소를 `/progress/[code]`로 바꿔 보낸다 (`app/lib/site-analytics.tsx`). 알림톡 버튼은 코드를 알리고와
  카카오로 실어 보낼 수밖에 없다.
- 휴지통에 있는 현장은 없는 현장으로 본다. Firestore를 쓰지 않는 환경에서는 링크가 꺼진 것과 같게 보인다.
- 코드로 현장을 찾을 때는 서버(Firestore 서비스 계정)에서만 읽는다. 브라우저는 Firestore에 직접 접근하지 않는다.

### 뒷자리 확인

1. 코드가 없거나 `progressEnabled`가 꺼져 있으면: "링크가 꺼져 있습니다. 위브디자인(031-381-0489)으로 문의해 주세요."
2. 유효한 쿠키가 없으면 "휴대폰 번호 뒷자리 4자리" 입력 화면을 보여준다.
3. `POST /api/progress/verify { code, last4 }`
   - 고객 번호는 휴대폰을 우선한다. 현장의 휴대폰 → 연결된 고객(`customerId`)의 휴대폰 → 현장의 번호 → 고객의 번호 순이다
     (`app/api/manager/_customer-phone.ts`). 뒷자리 확인, 쿠키, 알림톡이 모두 이 같은 번호를 쓴다. 숫자만 비교한다.
   - 고객 번호가 없으면 확인할 수 없다는 안내 (관리자 화면은 링크를 켤 때 경고한다).
   - 번호를 맞춰 보는 확인은 잠금으로 거절되지 않았다면 맞든 틀리든 답하기 전에 결과를 기록한다. `progressAccess`만, 읽은 시점의
     `updateTime`을 조건으로 걸어 쓴다. 기록하지 못하면 (다른 확인이나 직원의 수정과 겹침, 저장소 오류) 맞든 틀리든 같은 503
     "잠시 후 다시 시도해 주세요."로 답하고 쿠키는 주지 않는다. 그래서 동시에 들어온 추측이 세어지지 않거나 잠금을 지우는 일,
     연타 속에서 맞는 번호가 기록 없이 쿠키를 받아 가는 일이 없다.
   - 성공: 기록한 뒤 쿠키 `wp_<sha256(code) 앞 16자>` = `exp.HMAC(key, code|고객 번호 전체 숫자|exp)`, 180일,
     `HttpOnly; Secure; SameSite=Lax; Path=/progress`. 실패 횟수와 잠금은 처음 상태로 돌아가고 `lastOkAt`이 남는다.
   - 실패: `failedCount + 1`. 5회가 되면 잠긴다. 첫 잠금은 15분이고, 마지막 성공 뒤 잠금이 한 번 더 걸릴 때마다 시간이 두 배가 된다
     (30분, 1시간, … 최대 24시간). 잠금이 끝나면 실패 횟수는 다시 0부터 세지만 잠금 횟수(`lockCount`)는 이어진다. 맞게 입력하거나 새
     코드를 만들면 처음(15분)부터 다시 시작한다.
   - 잠긴 동안은 확인하지 않고, 틀려도 시간을 늘리거나 세지 않는다. 423과 남은 시간을 시간·분으로 안내한다: "확인 시도가 너무 많습니다.
     15분 뒤에 다시 시도해 주세요.", "… 1시간 30분 뒤에 …", "… 24시간 뒤에 …" (분 단위로 올림).
4. 서명 키: 보안 강화 설계와 같은 순서로 정한다. `MANAGER_SESSION_SECRET`에서 `HMAC(secret, "weve-progress-v1")`로
   파생, 없으면 `SANITY_WRITE_TOKEN`에서 같은 방식으로 파생. 둘 다 없으면 확인 API가 500. `MANAGER_SESSION_SECRET`은 32바이트 이상의
   무작위 값이어야 한다 (§8).
5. 쿠키는 코드와 고객 번호 전체(뒷자리만이 아니라 모든 숫자)에 묶여 있다. 새 링크로 바꾸면 코드가 바뀌어 예전 쿠키와 링크가 모두
   무효가 되고 실패 기록과 잠금도 처음 상태가 된다. 번호의 어느 숫자가 바뀌어도 쿠키가 무효가 되고, 뒷자리만 같은 다른 번호로는
   통과하지 못한다.

### 화면 구성 (휴대폰 우선)

1. 위브디자인 로고, 현장명, "OOO 고객님의 공사 진행 현황"
2. 진행률 바, 공사 기간(첫 공정 시작일 ~ 마지막 공정 종료일), 지금 공정 / 다음 공정
3. 공정 일정 목록: 완료 ✓ / 진행 중 / 예정, 공정 이름과 날짜
4. 진행 기록: 날짜별 카드(최신순), 담당 실장 이름, 작업 메모, 사진 격자. 사진을 누르면 크게 보고 좌우로 넘긴다.
5. 문의: 회사 대표번호 전화 버튼

### 공정과 진행률 계산

- 기준 견적: 해당 현장의 `versionType === 'final'` 중 가장 최근, 없으면 가장 최근 버전의 `scheduleJson`.
- 공정 상태 (한국 시간 기준 오늘): `endDate < 오늘` 완료, `startDate <= 오늘 <= endDate` 진행 중, 그 외 예정.
  공정의 `progress` 값이 100이면 날짜와 상관없이 완료로 본다.
- 전체 진행률: 공정별 진행도(`progress`가 0보다 크면 그 값, 0이거나 없으면 날짜 상태로 예정 0 / 진행 중 50 / 완료 100)를
  `durationDays`로 가중 평균 (`durationDays`가 없거나 시작~종료 일수보다 작으면 시작~종료 일수를 쓴다).
  `progress` 기본값이 0이므로 0은 "입력 안 함"으로 본다.
- 이름이 없거나 날짜가 올바르지 않거나 시작일이 종료일보다 늦은 공정은 건너뛰고, 나머지는 시작일 순으로 보여준다.
- 공정 일정이 없으면 진행률 영역을 숨기고 진행 기록만 보여준다.

### 보여주지 않는 것

견적 금액, 단가, 원가, 마진, 거래처 이름·연락처, 공정 메모(`memo`), 담당 실장 외 직원 정보.

## 4. 관리자 화면

### 현장 정보: "고객 진행 현황 링크"

- 링크 켜기·끄기. 코드가 없으면 켤 때 만든다. 고객 번호가 없으면 경고를 보여주고 켜지 않는다. 보통은 아래 "자동 생성과 자동 종료"가
  링크를 만들고 닫는다. 이 버튼은 직원이 링크를 직접 다시 켜거나 끌 때 쓴다.
- 링크 복사, 새 링크로 바꾸기(확인창: "이전 링크와 고객 확인 기록이 모두 무효가 됩니다"). 복사되는 주소는 Vercel Preview에서는
  그 브랜치의 미리보기 주소(`VERCEL_ENV=preview`일 때 `https://$VERCEL_BRANCH_URL`)라서 Preview에서 열리고, 그 밖에는
  `NEXT_PUBLIC_SITE_URL`, 없으면 `https://www.wevedesign.co.kr`이다.
- 미리보기: 관리자 세션으로 `GET /api/manager/progress?siteId=&preview=1`이 고객 화면과 같은 데이터를 돌려주고, 관리자
  화면 안에서 같은 컴포넌트로 보여준다. 뒷자리 확인을 하지 않는다.
- 알림톡 발송 기록 목록.

### 링크 자동 생성과 자동 종료 (대표님 결정, 2026-10-17)

- 처음 올릴 때 자동: 직원이 현장의 첫 진행 기록을 올리면(`createUpdate`) 서버가 코드를 만들고 링크를 켠다 (이미 '완료'인 현장은 제외). 켜는 별도 단계는 없다.
  새 코드와 함께 `progressCodeCreatedAt`과 실패 기록(`progressAccess`)도 새로 채운다.
- 고객 번호가 없는 현장은 링크를 만들지 않고 기록만 저장한다. 고객 번호를 넣은 뒤 올리는 기록부터 링크가 만들어진다.
- 이미 '완료'인 현장은 코드가 없으면 기록을 올려도 링크를 만들지 않는다 (고객 번호가 있어도 없어도 같다). '완료'는 링크를 닫는 상태라,
  끝난 현장의 첫 기록이 링크를 여는 일이 없게 한다. 이미 켜진 링크는 이 규칙이 닫지 않는다. 닫는 것은 '완료'로 바뀌는 순간뿐이다.
  필요하면 직원이 "링크 켜기"로 켠다.
- 이미 코드가 있는 현장은 링크 상태를 그대로 둔다. 직원이 끈 링크와 '완료'로 닫힌 링크는 기록을 올려도 다시 켜지지 않는다.
  다시 켜는 것은 직원이 "링크 켜기"로만 한다.
- 알림톡은 이 단계가 끝난 뒤의 링크 상태로 보낸다. 첫 기록을 올리면서 알림톡을 골라도 링크가 먼저 만들어져 보낼 수 있다.
  링크가 꺼져 있거나 고객 휴대폰 번호가 없으면 지금처럼 막는다.
- 완료 즉시 자동 종료: 현장 저장(`POST /api/manager/office`, `type: site`)으로 상태가 '완료'가 아니던 현장이 '완료'가 되면
  서버가 그 현장의 `progressEnabled`를 끈다. 코드와 실패 기록은 그대로 둔다.
- '완료'로 바뀌는 순간에만 닫는다. 끝난 현장의 링크를 직원이 손으로 다시 켜면, 그 뒤에 현장을 저장해도 다시 닫지 않는다.
- 두 동작 모두 서버가 정한다. 진행 현황 필드(`progressCode`, `progressEnabled`, `progressCodeCreatedAt`, `progressAccess`)는
  서버가 브라우저로 내려주는 현장 정보(목록, 휴지통, 저장 응답)에 실리지 않고, 브라우저가 보낸 현장 정보에 실려 와도 버린다.

### 일일 보고서 창

- 기존 "보고서 이미지 만들기"는 그대로.
- 추가: "고객 진행 현황에 올리기" (링크를 끈 현장이 아니면 기본 켜짐. 처음 올리면 링크가 자동으로 만들어진다. 이미 '완료'인 현장은 제외),
  "고객에게 알림톡 보내기" (기본 꺼짐). 템플릿 설정이 없거나, 고객 휴대폰 번호가 없거나, 이번 올리기 뒤에도 링크가 꺼져 있을
  것으로 보이면(끈 링크, 이미 '완료'인 새 현장) 고를 수 없고 이유를 보여준다.
- "올리기": 사진 줄이기 → 업로드 → 기록 저장 → (선택 시) 알림톡 발송. 진행 상태와 결과를 창 안에 보여준다.
- 방금 올린 내용(날짜·담당·메모·사진)과 같은 내용은 다시 올릴 수 없다 (두 번 눌러 기록과 알림톡이 두 번 나가는 것을 막는다).
  사진·메모·날짜·담당 중 하나를 바꾸면 새 기록으로 올릴 수 있다. 작업 날짜의 기본값은 한국 시간 기준 오늘이다.
- 이 현장의 서버 기록 목록: 날짜, 메모 요약, 사진 수, 알림 발송 여부, 삭제(확인창), 알림 다시 보내기.

### API (관리자 인증)

- `GET /api/manager/progress?siteId=` 링크 상태와 기록 목록
- `POST /api/manager/progress`
  - `multipart`: `uploadPhoto` (siteId, file 1장) → `{ photo: { assetId, url, width, height } }`. Vercel 요청 크기 제한(약 4.5MB)
    때문에 사진은 한 장씩 올린다. JPG·PNG·WEBP, 한 장 4MB 이하. 중립적인 이름으로 올리고, Sanity 데이터셋이 비공개일 때만 올라간다 (§2, §6).
  - JSON: `createUpdate` (siteId, reportDate, designer, workDetail, photos[] = uploadPhoto 결과, notify),
    `deleteUpdate` (id), `setLink` (siteId, `mode`: `enable` / `disable` / `rotate`), `notify` (updateId, `resend` 여부).
    기록 한 건은 사진 1~40장과 작업 메모(5000자 이하)가 필요하다.
  - `createUpdate` 응답: `{ update, notify?, link: { enabled, created, url, reason? } }`. `created`는 이번에 링크를 처음 만들었다는 뜻,
    `url`은 코드가 없으면 빈 문자열. `reason`은 `no-customer-phone`(고객 번호 없음), `link-off`(링크가 꺼져 있음),
    `site-done`(이미 '완료'인 현장이라 만들지 않음).
- `POST /api/manager/office` (`type: site`): 상태가 '완료'로 바뀌면 서버가 링크를 끈다 (위 "자동 생성과 자동 종료").
- 권한: 보안 강화 작업의 서버 권한 검사를 따른다. 이 API는 `sites` 권한을 요구한다 (관리자는 모든 권한을 가진다). 일일 보고서 창은
  대시보드에서 열리므로 진행 기록을 올리려면 '대시보드'와 `sites` 권한이 모두 필요하다. 현장 탭의 링크 패널은 `sites`만 있으면 된다.

## 5. 알림톡

- 알리고 발송 흐름은 기존 계약 완료 알림톡과 같은 방식(서버에서 `akv10/alimtalk/send`)을 쓴다.
- 받는 사람: §3의 고객 번호 (현장 휴대폰 → 연결된 고객 휴대폰 → 현장 번호 → 고객 번호 순). 고른 번호가 휴대폰이어야 하고 유선 번호는 막는다.
  기록 한 건당 한 번 발송, 다시 보내려면 `resend`.
- 변수: `#{고객명}`, `#{현장명}`, `#{날짜}`, 버튼 링크의 `#{코드}`. `#{코드}`는 버튼 링크에만 쓴다. 서버는 문구 안의 `#{코드}`도 바꾸지만,
  고객이 읽는 글에 링크 코드를 넣을 이유가 없고 노출만 늘어난다.
- 환경 변수

```text
ALIGO_PROGRESS_TEMPLATE_CODE=
ALIGO_PROGRESS_MESSAGE_TEMPLATE=   # 승인된 템플릿 문구와 글자까지 같아야 한다. 문구 줄만 넣고 버튼 줄은 넣지 않는다
ALIGO_PROGRESS_BUTTON_JSON=        # 한 줄 JSON. 승인된 버튼과 같게. 링크에 #{코드}. 기본값 없음
ALIGO_PROGRESS_SUBJECT=공사 진행 안내   # 선택
```

- 템플릿 코드, 문구, 버튼 세 값이 모두 있어야 발송한다 (제목만 선택). 서버가 버튼 JSON의 `#{코드}`를 현장 코드로 바꿔 보내고,
  `#{날짜}`는 기록의 작업 날짜를 "YYYY년 M월 D일"로 채운다.
- 버튼 값 (`ALIGO_PROGRESS_BUTTON_JSON`): 이미 보내지고 있는 관리자 페이지 버튼(`app/api/send-consultation/aligo-admin.ts`)과 같은
  모양이다. 한 줄로 Vercel에 넣는다.

```text
{"button":[{"name":"진행 현황 보기","linkType":"WL","linkTypeName":"웹링크","linkMo":"https://www.wevedesign.co.kr/progress/#{코드}"}]}
```

- 템플릿 버튼은 모바일 링크만 등록하고 PC 링크는 비워 두기를 권한다 (위 값, 관리자 페이지 버튼과 같다). PC 링크도 채워 등록했다면 같은 객체
  안에 `"linkPc":"https://www.wevedesign.co.kr/progress/#{코드}"`를 더한다.

```text
{"button":[{"name":"진행 현황 보기","linkType":"WL","linkTypeName":"웹링크","linkMo":"https://www.wevedesign.co.kr/progress/#{코드}","linkPc":"https://www.wevedesign.co.kr/progress/#{코드}"}]}
```

- 버튼의 이름과 링크는 승인된 템플릿과 글자까지 같아야 한다. 다르면 발송이 실패로 남으므로("알림톡 발송 기록") 값을 다른 쪽으로 바꾼다.
- 공통 값 `ALIGO_API_KEY`, `ALIGO_USER_ID`, `ALIGO_SENDER_KEY`, `ALIGO_SENDER_PHONE`은 기존 것을 쓴다.
- `ALIGO_TEST_MODE=Y`(선택)는 Vercel의 Preview 환경에만 넣는다. test 모드에서는 알리고가 요청을 받아 주기만 하고 아무것도 보내지 않는데,
  앱은 보낸 것으로 기록한다. Production에 넣으면 진짜 실패가 가려지고, 보낸 것으로 기록된 글은 '이미 보낸 기록' 규칙 때문에 그냥 다시 보내기도
  막힌다. Preview에도 `ALIGO_PROGRESS_*` 값(과 공통 값)이 있어야 미리보기 시험에서 발송까지 간다.
- 템플릿 예시 (대표님이 알리고에 등록하고 승인받는다)

```text
[위브디자인] 공사 진행 안내
#{고객명} 고객님, #{현장명} 현장의 #{날짜} 공사 진행 상황이 등록되었습니다.
아래 버튼을 눌러 사진과 공정 일정을 확인해 주세요.
문의: 031-381-0489

버튼(웹링크) 진행 현황 보기
  모바일웹 링크: https://www.wevedesign.co.kr/progress/#{코드}
  PC 링크: 비워 둠
  채널추가: 체크하지 않음 (정보성 알림톡)
```

- 위 첫 네 줄(문구)만 `ALIGO_PROGRESS_MESSAGE_TEMPLATE`에 넣는다. `버튼(웹링크)`부터는 알리고에 등록하는 버튼 설명이라 넣지 않는다.
- 버튼은 기존 알림톡과 같은 `button_1` 필드로 보낸다. 변수 링크(`#{코드}`) 형식은 미리보기 배포(`ALIGO_TEST_MODE=Y`)와 첫 실제 발송에서
  다시 확인한다. 버튼 링크는 항상 운영 도메인을 가리키므로, 진짜 알림톡의 링크는 병합·배포 뒤에야 열린다.

## 6. 오류 처리

| 상황 | 처리 |
|---|---|
| 사진 업로드 실패 | 기록을 만들지 않는다. 실패한 사진 이름과 다시 시도 안내 |
| 기록 저장 성공, 알림톡 실패 | 기록은 남긴다. `notifyLog`에 실패 이유, 창에 "다시 보내기" |
| 템플릿 환경 변수 없음 | "알림톡 템플릿 설정이 필요합니다". 기록 올리기는 그대로 된다 |
| 고객 번호 없음 | 링크 켜기와 알림 발송을 막고 안내 |
| 고객 번호 없는 현장의 첫 기록 | 기록만 저장하고 링크는 만들지 않는다 (`reason: no-customer-phone`). 번호를 넣은 뒤 올리는 기록부터 만들어진다 |
| 링크가 꺼진 현장에 기록 올리기 | 기록은 저장한다. 링크는 다시 켜지 않는다 (`reason: link-off`). 알림톡은 막는다 |
| 이미 '완료'인 현장의 첫 기록 | 기록은 저장한다. 링크는 만들지 않는다 (`reason: site-done`, 고객 번호가 없어도 같다). 알림톡은 막는다. 필요하면 직원이 "링크 켜기"로 켠다 |
| 첫 기록의 링크 만들기 실패 | 기록을 저장하지 않고 오류를 보여준다. 다시 올리면 된다 (기록이 두 번 생기지 않는다) |
| 현장을 '완료'로 저장했는데 링크 닫기 실패 | 현장 저장은 성공으로 둔다. 서버 로그만 남기고, 링크는 켜진 채이므로 직원이 "링크 끄기"로 닫는다 |
| 코드 없음/링크 꺼짐 | 고객 페이지 안내 화면 (어떤 현장인지 드러내지 않는다) |
| 뒷자리 5회 실패 | 15분 잠금. 잠금이 풀린 뒤 5회 더 틀리면 30분, 1시간, … 최대 24시간으로 늘어난다. 맞게 입력하거나 새 링크로 바꾸면 처음(15분)부터. 남은 시간은 시간·분으로 안내: "확인 시도가 너무 많습니다. 1시간 30분 뒤에 다시 시도해 주세요." |
| 확인 결과를 저장하지 못함 (다른 확인·직원 수정과 겹침, 저장소 오류) | 맞든 틀리든 같은 503 "잠시 후 다시 시도해 주세요." (`Retry-After: 2`). 쿠키를 주지 않고 틀린 횟수로도 세지 않는다 |
| Sanity 데이터셋이 공개 상태 | 사진 올리기를 막는다. 503 "사진 저장소(Sanity)가 공개 상태라 고객 사진을 올릴 수 없습니다. 관리자에게 비공개 전환을 요청해 주세요." 기록은 사진이 있어야 올릴 수 있어서, 비공개가 될 때까지 올릴 수 없다 |
| Sanity 상태를 확인하지 못함 (응답 오류, 시간 초과) | 사진 올리기를 막는다. 503 "사진 저장소 상태를 확인하지 못했습니다. 잠시 후 다시 시도해 주세요." |
| Firestore를 쓰지 않는 환경 | 관리자 API는 503 "진행 현황 기능은 Firestore 설정이 필요합니다.", 고객 페이지는 링크 꺼짐 안내 |

## 7. 검증

1. 단위 스크립트: 쿠키 서명·검증·만료, 코드 교체 후 무효, 잠금 계산, 진행률 계산(진행도 값 있음/없음, 공정 없음).
2. 로컬 화면(내장 브라우저, API는 fetch 모킹): 일일 보고서 창 올리기 흐름, 기록 목록·삭제, 링크 켜기/끄기/바꾸기, 미리보기.
3. 고객 페이지: 뒷자리 확인 성공/실패/잠금, 링크 꺼짐, 휴대폰 크기 화면, 금액·거래처 정보가 응답에 없는지 확인.
4. `npm run build` 통과.
5. 병합 전에 Vercel Preview에서 `ALIGO_TEST_MODE=Y`(Preview에만)로 알림톡 요청 형식 확인. 실제 발송은 병합·배포 뒤 템플릿이 승인되면
   대표님 번호로 한 번.
6. Preview(실제 Firestore)에서 확인: 뒷자리 확인 401·423·200, 거의 동시에 틀린 두 번이 401 하나와 503 하나로 나뉘는지, 링크 켜기·끄기·새 링크,
   링크가 없는 현장의 첫 기록, '완료' 저장이 링크를 닫는지, 링크가 있는 현장을 사무 화면에서 저장해도 `progressCode`가 그대로인지.
   Firestore의 조건부 쓰기는 로컬에서 실제 Firestore로 돌려 보지 못했다.

## 8. 배포 순서 (대표님 작업)

### 배포 전 준비

Preview 확인과 병합에 앞서 아래를 끝낸다.

1. **Sanity 먼저.** Sanity에서 Viewer 토큰을 만들어 Vercel(Production과 Preview)에 `SANITY_READ_TOKEN`으로 넣고 다시 배포한다.
   그 다음에 `production` 데이터셋을 비공개로 바꾼다. 순서가 중요하다. 토큰 없이 비공개로 바꾸면 공개 사이트의 포트폴리오가 비어 보인다.
   데이터셋이 비공개가 되기 전에는 사진 올리기가 코드의 안내 문구("사진 저장소(Sanity)가 공개 상태라 고객 사진을 올릴 수 없습니다.
   관리자에게 비공개 전환을 요청해 주세요.")로 막힌다.
2. Firestore 보안 규칙이 사무 컬렉션(`officeSites`, `officeCustomers` 등)과 `siteProgressUpdates`에 대한 브라우저의 직접 접근을 막는지
   확인한다. 진행 현황 코드가 `officeSites`에 들어 있어서, 규칙이 열려 있으면 Firebase 토큰을 가진 브라우저가 코드를 직접 읽을 수 있다.
3. `MANAGER_SESSION_SECRET`은 32바이트 이상의 긴 무작위 값이어야 한다. 고객 쿠키는 이 값에서 파생한 키로 서명한다 (§3).
4. `ALIGO_TEST_MODE=Y`는 Vercel의 Preview 환경에만 넣는다 (§5).

### 순서

1. 알리고에 5절(알림톡)의 템플릿을 등록하고 승인을 받는다 (보통 1~3일). 2026-10-17 대표님이 등록 진행 중.
2. 승인되면 Vercel에 `ALIGO_PROGRESS_*` 값을 넣는다. Preview 환경에도 넣어야 미리보기 시험이 발송까지 간다. 버튼 값은
   `docs/KAKAO_BIZFORM_SETUP.md`의 한 줄을 쓴다.
3. **병합 전에 Vercel Preview에서 확인한다.** 이 브랜치의 미리보기 배포에서 한다 (운영에서 하는 단계가 아니다). 테스트 현장을 하나 만들고
   고객 번호에 대표님 본인 휴대폰 번호를 넣는다. 일일 보고서에 사진을 붙여 "고객 진행 현황에 올리기"로 올리면 링크가 자동으로 만들어진다
   (켜는 단계 없음). Preview에서 복사한 링크는 그 브랜치의 미리보기 주소(`https://$VERCEL_BRANCH_URL`)라서 Preview에서 열린다.
   휴대폰으로 그 링크를 열어 뒷자리 확인(틀리게 5번 입력하면 잠금), 사진·공정·메모 표시, 금액이 보이지 않는지를 확인한다. 현장을 '완료'로
   저장하면 링크가 꺼지는지도 본다. 알림톡은 test 모드라 실제로 오지 않고 발송 기록만 남는다. 알림톡 버튼은 항상 운영 도메인을
   가리키므로, 진짜 알림톡의 링크는 병합·배포 뒤에야 열린다.
4. 확인을 마치고 PR 검토를 끝내면 이 기능을 병합·배포한다. 앞선 묶음(보안 포함, #11)은 main에 이미 병합되어 있다.
5. 병합·배포 뒤 템플릿이 승인되어 있으면 대표님 번호로 알림톡을 한 번 실제로 보내 본다 (`ALIGO_TEST_MODE`가 Production에 없어야 한다).
